# Google Region Monitor — Chrome extension v1.9.4

Расширение Manifest V3 для мониторинга Google Search по страновым профилям. В каталоге 19 стандартных профилей из методичек по Латинской Америке, Южной Азии, Восточной и Юго-Восточной Азии. Профили можно объединять в произвольные группы (например, «Южная Азия»), а поисковые выражения внутри каждого профиля — в пользовательские группы с любыми названиями. Ни названия, ни тематика групп не зашиты в код. Также доступны локальные пользовательские профили, синхронизация стандартных профилей из GitHub, минимальный глобальный интервал между переходами Google, последовательная пагинация, выгрузка диагностического лога 2Captcha, экспорт HTML-отчёта и опциональная фильтрация региональной принадлежности СМИ через веб-версию ChatGPT.

Поиск использует параметр `filter=0`, чтобы Google включал результаты, которые обычно скрывает как очень похожие на уже показанные. Этот параметр повторно добавляется к ссылкам пагинации. Страницы обходятся последовательно и с общей пользовательской задержкой; `num=100` не используется. Google CAPTCHA и другие защитные ограничения не обходятся.

## Релиз 1.9.4 — прямые URL из источников до обращения к Google

- Перед запросом к Google `/goto` расширение ищет прямые HTTP(S)-адреса в структурированных полях результата 2captcha (`url`, `link`, `target_url`, `destination_url`, `original_url` и поддерживаемые варианты).
- В HTML Google проверяются `href`, `data-url`, `data-href`, `data-dest-url`, `data-target-url`, `data-original-url`, `data-lpage` и URL в атрибуте `ping`; opaque-токены `CAES...` не считаются адресами.
- При объединении JSON и HTML данные HTML больше не отбрасываются только из-за совпадения заголовка: найденный прямой адрес и домен из `<cite>` дополняют структурированный результат.
- Если точный адрес не найден в JSON/HTML, используется прежнее резервное разрешение `/goto`. Домен из видимой строки Google выводится отдельно как подсказка и не подменяет ссылку на статью.
- В отчёт добавлена статистика источников URL: JSON 2captcha, HTML и резервное перенаправление Google.
- Проверено 38 автоматических тестов. Реальный браузерный запрос к Google в этой сборке отдельно не выполнялся.

## Релиз 1.9.3 — улучшено разрешение Google /goto

- Добавлено чтение HTTP-заголовка `Location` через `webRequest.onHeadersReceived`, в том числе когда Google возвращает его не в обычном 3xx-ответе.
- Сохранён `onBeforeRedirect` как резервный канал получения адреса; оба обработчика ограничены `https://www.google.com/goto*`.
- Тайм-аут ожидания ответа увеличен до 12 секунд.
- Конечный URL по-прежнему проверяется: допускаются только HTTP(S)-адреса, а вложенные Google redirect-ссылки не принимаются как конечный результат.
- Абсолютная успешность не гарантируется: если Google не прислал `Location`, токен истёк или запрос отклонён, исходная ссылка остаётся в отчёте.

## Релиз 1.9.2 — прямые ссылки вместо Google /goto

- Новые ссылки Google вида `google.com/goto?url=CAES…` разрешаются по HTTP-заголовку `Location` без декодирования непрозрачного токена.
- Запрос выполняется без перехода на сайт назначения; в отчёт записывается конечный HTTP(S)-адрес.
- Преобразование применяется перед фильтрацией ChatGPT и созданием отчёта. Не разрешённые Google ссылки сохраняются как есть и учитываются в диагностике.

## Релиз 1.9.1 — упрощение API и исправление статистики 2Captcha

- Удалена встроенная консоль ручных тестовых запросов 2Captcha; обычный мониторинг, API-ключ и экспорт диагностического лога сохранены.
- В режиме **2Captcha Google Search API** один поисковый запрос создаёт одно задание с `page_num` от 1 до 10. Для нескольких страниц HTML запрашивается в том же ответе через `with_html: true`; дополнительные offset-задания больше не создаются.
- В режиме **2Captcha Scrape** сохранён отдельный запрос `task_type: "scrape"` на каждую страницу: этот метод получает HTML конкретного URL и не заменяется на `google_search`.
- Кнопка обновления статистики теперь отдельно по нажатию получает баланс и историю `google_search`/`scrape`. Средняя цена рассчитывается по завершённым заданиям со статусом `done`, а стоимость последнего отчёта — по его `response_id` и фактическому полю `price` из истории.
- История расходов не загружается автоматически при открытии расширения или создании отчёта. Внутреннее поле `x-debug.price` не используется для расчёта стоимости.

## Исправление 1.10.1 — детектор CAPTCHA для Scrape

Google Search вставляет в обычную страницу результатов JavaScript-код с переменными и обработчиками CAPTCHA (например, `hasCaptchaSupport=true` и общий путь `/sorry/index`). Эти строки сами по себе не означают, что Google показал проверку. Начиная с v1.10.1 Scrape-парсер анализирует видимый текст и реальные элементы challenge-формы, исключая `script`, `style` и другие невидимые блоки. Это предотвращает ложную остановку на обычной SERP.

## Установка

1. Распакуйте архив в отдельную папку.
2. Откройте `chrome://extensions`.
3. Включите **Режим разработчика**.
4. Нажмите **Загрузить распакованное** и выберите эту папку.
5. Закрепите значок расширения на панели Chrome, чтобы быстро открывать боковую панель.

## Как применяются язык и страна

Расширение не открывает Google Preferences и не меняет настройки Google. Язык интерфейса (`hl`), страна (`gl`) и фильтр языка результатов (`lr`) передаются прямо в ссылке каждого поискового запроса. При смене профиля достаточно выбрать его — вкладки Google открывать не нужно.

## Группы профилей и группировка списка

В каждом профиле есть поле **«Группа профилей»**. Чтобы собрать несколько стран в один набор, укажите у них одно и то же название, например «Южная Азия», «Латинская Америка» или своё. Название можно выбрать из подсказок или ввести новое. Группы создаются автоматически по значениям этого поля; отдельный фиксированный список регионов в коде не используется.

Оба выпадающих списка профилей — в разделе «Профили» и в разделе «Мониторинг» — строятся по `profileGroup`. Названия групп сортируются по русскому алфавиту, профили внутри группы также сортируются по алфавиту. Профили без значения `profileGroup` помещаются в «Без группы». Порядок элементов в JSON не определяет порядок интерфейса.

## Произвольные группы поисковых запросов

В редакторе профиля можно добавлять и удалять группы запросов, менять их названия и состав. Каждая строка внутри группы — отдельный запрос Google. Расширение отображает названия этих групп над соответствующими чекбоксами в «Мониторинге». Например, можно самостоятельно создать группы «Новости отрасли», «Проекты компании», «Социальные сети», «Литий» — это примеры пользовательских названий, а не встроенные категории.

Классификации запросов по ключевым словам компании или заранее заданным темам в коде нет. Перемещение запроса в группу выполняется через редактор профиля. При запуске мониторинга отмеченные запросы собираются из всех выбранных групп; на запуск не влияют названия групп.

## Модель профилей

Расширение объединяет три источника профилей:

- **Стандартные · GitHub** — загружаются из файла конфигурации в GitHub-репозитории.
- **Встроенный каталог** — профили из `config/standard-profiles.json` внутри архива. Он дополняет каталог, если удалённый JSON ещё не содержит часть стандартных профилей.
- **Мои профили · локально** — пользовательские записи в `chrome.storage.local`; синхронизация GitHub их не удаляет и не перезаписывает.

Переименование стандартного профиля и изменение его `profileGroup` сохраняются как локальное переопределение без создания копии и не меняют общий каталог. Если изменить язык, регион или группы поисковых запросов стандартного профиля, обычная кнопка «Сохранить профиль» создаёт локальную пользовательскую копию, оставляя стандартную запись нетронутой. При наличии Fine-grained token можно отправить изменённые значения стандартного профиля в GitHub кнопкой **«Сохранить изменения стандартного профиля в GitHub»**. Для переименования в общем каталоге используйте её после изменения названия.

Стандартный профиль можно скрыть локально (если он только во встроенном каталоге) или удалить из GitHub (если он опубликован там). Пользовательские профили удаляются только локально.

## Конфигурация стандартных профилей

Используется `config/standard-profiles.json` в репозитории `artemmalkin/Google-Region-Monitor`, ветка `master`. Эти значения заданы в `github-config.js`.

```json
{
  "schemaVersion": 1,
  "updatedAt": "2026-11-23T00:00:00.000Z",
  "profiles": [
    {
      "id": "india",
      "name": "Индия",
      "profileGroup": "Южная Азия",
      "interfaceLang": "en",
      "resultLangs": "en, hi",
      "region": "IN",
      "queryGroups": [
        {
          "id": "industry",
          "name": "Атомная энергетика и промышленность",
          "queries": [
            "site:.in (\"nuclear energy\" OR \"nuclear power plant\" OR NPCIL OR SMR)"
          ]
        },
        {
          "id": "social",
          "name": "Социальные сети",
          "queries": [
            "(site:x.com OR site:facebook.com OR site:instagram.com) India (nuclear OR NPCIL)"
          ]
        }
      ],
      "queries": [
        "site:.in (\"nuclear energy\" OR \"nuclear power plant\" OR NPCIL OR SMR)",
        "(site:x.com OR site:facebook.com OR site:instagram.com) India (nuclear OR NPCIL)"
      ]
    }
  ]
}
```

Поля профиля:

| Поле | Значение |
|---|---|
| `id` | Уникальный постоянный ID профиля: латиница, цифры, `.`, `_`, `-` |
| `name` | Название профиля, отображаемое в расширении |
| `profileGroup` | Необязательное имя группы страновых профилей; одинаковое значение объединяет профили в одну группу |
| `interfaceLang` | Язык Google (`hl`), например `vi`, `en`, `id` |
| `resultLangs` | Фильтр языков (`lr`), строка через запятую или массив, например `"vi, en"` |
| `region` | Страна поиска (`gl`), например `VN`, `ID`, `BD` |
| `queryGroups` | Необязательный массив произвольно именуемых групп; каждая группа содержит `id`, `name` и массив `queries` |
| `queryGroupsRevision` | Версия структуры групп запросов. Используется для однократного перехода со старого каталога на новую разбивку; после публикации профиля текущей версии удалённые группы и запросы становятся авторитетными |
| `queries` | Совместимый со старыми версиями плоский массив поисковых строк. В новой версии при наличии непустого `queryGroups` используется сгруппированная структура; `queries` сохраняется для старых клиентов и миграции. |

Пример одной группы:

```json
{
  "id": "company-projects",
  "name": "Проекты и партнёрства",
  "queries": ["company OR project OR local-project"]
}
```

`queryGroups` в синхронизируемом GitHub JSON — источник истины, если массив групп задан. Поэтому переименование/удаление группы или запроса в таком профиле не будет отменено встроенным каталогом при следующей синхронизации. Старые JSON, содержащие только `queries`, продолжают поддерживаться: их строки отображаются внутри одной группы «Основные запросы»; уникальные дополнительные старые строки сохраняются в группе «Дополнительные запросы».

## Синхронизация стандартных профилей

- Кнопка **Проверить обновление** проверяет GitHub Release и одновременно принудительно загружает стандартные профили из GitHub.
- Автоматическая синхронизация выполняется через `chrome.alarms` примерно раз в 24 часа, пока Chrome запущен.
- При запуске Chrome проверяется возраст локального кеша; если он актуален и источник тот же, лишняя загрузка не выполняется.
- При временной ошибке предыдущие стандартные профили сохраняются; встроенный каталог дополняет отсутствующие записи; пользовательские профили не затрагиваются.
- `queryGroupsRevision` сохраняется в локальном кеше при загрузке. Для профилей с актуальной ревизией группы и поисковые строки из GitHub остаются приоритетными, в том числе после удаления отдельных групп или запросов.

Для работы автоматической загрузки репозиторий и JSON должны быть доступны по адресу `raw.githubusercontent.com`.

## Пользовательские профили: импорт и экспорт

- **Экспорт профиля** выгружает выбранный пользовательский профиль, включая группы профилей и поисковых запросов.
- **Импорт из файла** принимает JSON, создаёт новую локальную копию с новым ID и не перезаписывает существующий профиль.
- Плоские старые профили автоматически мигрируют при открытии редактора в одну группу «Основные запросы»; исходные строки поиска сохраняются.

## Публикация и управление стандартными профилями в GitHub

Вставьте Fine-grained Personal Access Token в поле GitHub Fine-grained token. Требуется доступ только к целевому репозиторию и разрешение `Contents: Read and write`.

- **Добавить мой профиль в GitHub** — публикует выбранный локальный пользовательский профиль, включая `profileGroup` и `queryGroups`.
- **Сохранить изменения стандартного профиля в GitHub** — обновляет выбранный профиль по постоянному `id`, включая его название, группу профилей и группы запросов.
- **Кнопка × рядом с выбором профиля** — скрывает встроенный профиль локально или удаляет запись из GitHub после подтверждения.

Локальные переименования стандартного профиля не перезаписывают GitHub JSON автоматически. Чтобы поделиться переименованием/группой со всеми пользователями каталога, подтвердите сохранение в GitHub.

Токен хранится в локальном хранилище расширения Chrome; он не записывается в `github-config.js`, экспорт профиля или JSON конфигурации.

## Обновления самого расширения

В репозитории добавлен workflow `.github/workflows/release.yml`. Чтобы опубликовать новую версию:

1. Увеличьте `version` в `manifest.json`.
2. Отправьте изменения в GitHub.
3. Создайте тег, совпадающий с версией, например `v1.8.1`.
4. GitHub Actions соберёт `google-region-monitor.zip` и прикрепит его к Release.
5. Расширение сможет проверить Release и предложить скачать обновление.

Для уже установленного распакованного расширения Chrome требует ручной перезагрузки после получения обновлённой папки.


## Мониторинг выбранных запросов и остановка (v1.4.3)

В разделе «Мониторинг» отметьте только запросы, которые нужно включить в отчёт. Кнопка «Сформировать отчёт» использует непосредственно состояние этих флажков: список больше не перестраивается перед запуском и не сбрасывает выбор.

Во время сбора доступна кнопка «Остановить». Она прерывает ожидание текущей незавершённой страницы, не добавляет её в отчёт и формирует HTML-отчёт по уже собранным страницам. В шапке отчёта указывается, был ли мониторинг завершён полностью или остановлен пользователем. При включённой опции автоматического восстановления после остановки также применяется русский профиль Google.

## Поиск и сбор выдачи

В версии 1.5.4 добавлен общий минимальный интервал между поисковыми запросами Google (0–600 секунд, по умолчанию 2 секунды). Ограничитель находится в background service worker и сериализует выдачу слотов между окнами расширения; интервал применяется к первому открытию страницы поиска, всем переходам пагинации и новым запросам в очереди. Время последнего поискового перехода сохраняется в локальном хранилище. Значение 0 отключает задержку. Если Google явно показывает CAPTCHA или ограничение, оставшиеся запросы запуска не отправляются.

- В поисковой выдаче поддерживаются контейнеры `#rso .MjjYud`, сниппеты `.VwiC3b`/`.yXK7lf` и пагинация `a#pnnext` (с альтернативными селекторами).
- Поисковые URL получают параметры `hl`, `lr`, `gl` и `tbs=qdr:*`.
- Google CAPTCHA, согласия и иные защитные ограничения не обходятся.

В присланном HTML выдачи используется индонезийский интерфейс (`lang="id"`), контейнеры результатов `.MjjYud`, блок `#rso`, сниппеты `.VwiC3b` и ссылка пагинации `#pnnext`. Эти селекторы теперь стоят первыми в алгоритме сбора.


## Режим 2Captcha Scrape (v1.10.0)

В разделе «Мониторинг» доступен отдельный источник **«2Captcha Scrape (HTML каждой страницы)»**. В отличие от `google_search`, этот режим не использует структурированный парсер Search API: для каждой выбранной страницы расширение отправляет собственное задание `task_type: "scrape"` на `/tasks/sync` с `data_format: "raw"` и `format: "json"`. Полученное поле `body` разбирается локально в расширении — извлекаются заголовки, ссылки и сниппеты из Google HTML.

Пагинация выполняется прямыми URL Google: первая страница — без `start`, вторая — `start=10`, третья — `start=20` и далее с шагом 10. Параметры выбранного профиля и периода (`hl`, `gl`, `lr`, `tbs`) сохраняются; `filter=0` также передаётся в URL этого режима. Для каждой страницы создаётся отдельное API-задание, поэтому число заданий равно числу реально запрашиваемых страниц на каждый поисковый запрос. Задания выполняются последовательно с паузой 750 мс.

При ответе Google с CAPTCHA/ограничением автоматических запросов или целевым HTTP 403/429 дальнейшие страницы и запросы не отправляются. Успешно загруженная HTML-страница включается в отчёт даже тогда, когда парсер не нашёл в ней органических результатов. Неудачно загруженные страницы помечаются как отсутствующие.

Старый вариант **«2Captcha Google Search API»** оставлен без изменений для сравнения. Сначала рекомендуется проверить Scrape на одном запросе и 2–3 страницах, сравнить HTML-отчёт и скачанный JSON API-лог, затем увеличить объём мониторинга. Кнопка скачивания лога не создаёт дополнительных запросов к 2Captcha; в файле сохраняются тела запросов/ответов, а API-ключ и Authorization маскируются.

## Режим 2Captcha Google Search API (v1.9.2)

Во вкладке «Мониторинг» можно выбрать **2Captcha Google Search API** вместо поиска в локальном браузере. Ключ хранится в `chrome.storage.local`; запросы выполняются через `scraper.2captcha.com`, без открытия Google в личном браузере.

Для каждого выбранного поискового выражения создаётся **одно** задание `task_type: "google_search"`. В его JSON передаётся `page_num`, равный выбранному числу страниц (1–10), а URL остаётся базовым — без `start`, `num` и `filter`. При выборе более одной страницы в том же задании включается `with_html: true`. Структурированные `groups.organic.items` и HTML страниц объединяются по абсолютным номерам `page_position.page`; если часть страниц не пришла, они отмечаются как отсутствующие, повторные задания для них не создаются.

Таким образом, в режиме Google Search API количество заданий на один поисковый запрос не зависит от выбранного числа страниц: **одно задание на запрос**, а не по одному заданию на каждую страницу. Ограничение 2Captcha для `page_num` — от 1 до 10.

Режим **2Captcha Scrape (HTML каждой страницы)** работает иначе и сохранён отдельно: он отправляет по одному `task_type: "scrape"` заданию на страницу с URL-параметром `start=0`, `start=10`, `start=20` и далее. HTML из `body` разбирается локально. Не следует путать стоимость этих двух режимов: у Scrape задание по-прежнему создаётся на каждую страницу.

### Статистика и стоимость

Кнопка **«Обновить статистику»** запускает отдельные запросы `getBalance` и `GET /task_history` для типов `google_search` и `scrape`. Автоматических запросов к истории нет. Для оценки среднего расхода используются последние доступные завершённые задания выбранного метода (`google_search` или `scrape`) со статусом `done` и числовым `price`; оценка числа доступных заданий — это баланс, делённый на среднюю цену этого метода.

После каждого отчёта расширение сохраняет его `response_id`. При следующем ручном обновлении истории фактические цены сопоставляются с этими ID, и стоимость последнего отчёта показывается только после подтверждения всех его заданий историей. Если ID ещё не появились в истории или история недоступна, сумма не угадывается и остаётся пустой. Внутренний `x-debug.price` намеренно не используется: для биллинга применяется `price` из `task_history`.

После завершения мониторинга через 2Captcha доступна кнопка **«Скачать лог запросов и ответов 2Captcha»**. Она сохраняет уже собранные данные и не отправляет дополнительные запросы; API-ключ и `Authorization` маскируются. Лог может содержать поисковые запросы и результаты Google, поэтому проверьте его перед публикацией в открытом репозитории.

## Версия 1.4.6 — фильтр региональных СМИ через ChatGPT

В версии 1.4.6 впервые добавлен AI-фильтр региональности: расширение собирает уникальные ссылки из Google-результатов и передаёт их в веб-версию ChatGPT пакетами. В версии 1.4.7 интеграция обмена заменена на рабочую реализацию из приложенного расширения-примера: `chatgpt_content.js` и `startNewChatGPTChat()` перенесены без изменений; каждый пакет отправляется в отдельном новом чате через протокол `chatgpt_request` / `chatgpt_response_ready`.

Проверка включается и выключается чекбоксом в разделе «Мониторинг»; настройка сохраняется локально. При включённой проверке ChatGPT получает домен, URL, заголовок, сниппет и поисковый запрос, а затем возвращает JSON со списком исключаемых ID. Расширение принимает только ID из текущего пакета и удаляет соответствующие ссылки со всех страниц отчёта, включая повторы. При выключенной проверке или ошибке ChatGPT все найденные ссылки остаются в отчёте.

Рабочий код из примера не переключает reasoning/model mode ChatGPT — он отвечает только за открытие нового чата, отправку сообщения и получение ответа. Поэтому расширение больше не пытается нажимать самописные кнопки выбора режима, которые могли задевать посторонние элементы интерфейса. Для работы требуется активная авторизация в `https://chatgpt.com/`.

## v1.9.8 — corrected 2Captcha offset range

- Page 1 is requested as a separate task with `page_num: 1` and no `start` offset.
- For exactly two requested pages, page 2 uses `start=10` without `page_num`, matching the documented single-page mode.
- For three or more requested pages, the second task uses `start=10` and `page_num=N-1` to collect the remaining absolute range from page 2 through page N.
- Removed the previous `start=20` + `page_num=1` request pattern, which returned `no_results` in the v1.9.7 diagnostic log.
- The monitor makes no more than two sequential API tasks per query; automatic balance and history requests remain disabled.

## v1.9.7 — offset-based multi-page pagination for 2Captcha

- Page 1 used the base URL with `page_num=1`; page 2 used `start=10` without `page_num`; pages 3–N used `start=20` with `page_num=N-2`.
- Requests ran sequentially with a 750 ms pause; a 3–10-page search used up to three API tasks per query.
- Structured `page_position.page` values were treated as absolute. The extension did not relabel a page-1 response as a later page when a worker ignored `start`.
- HTML and structured organic results were merged within their requested absolute page ranges; missing pages were reported, not invented.
- API logs recorded each request's range, offset, `page_num`, response ID, status, and returned HTML/structured page counts.

## v1.9.5 — 2Captcha API diagnostics and downloadable logs

- A **Download 2Captcha API log** button appears after a 2Captcha run when diagnostic events are available.
- The JSON log includes request endpoints and parameters, safe headers, HTTP statuses, selected response headers, raw response bodies, polling exchanges, and network errors.
- The log can be downloaded without making extra requests to 2Captcha. API keys and Authorization values are redacted.

## v1.9.4 — reliable multi-page 2Captcha collection

- Use the documented `pages` parameter for the initial multi-page request.
- Fall back to separate `start=10`, `start=20`, etc. requests for missing pages; those tasks omit the multi-page parameter.
- Run fallback requests sequentially with a short delay; never launch page requests concurrently.
- Handle synchronous `408/pending` responses by retrieving the same task through its `response_id`, rather than creating a duplicate search task.
- Show the actual number of API tasks and collected pages in the monitoring log.
- Remove the redundant log suffix about balance/history requests; automatic balance and task-history calls remain disabled.

## v1.9.3 — 2Captcha paging and reduced API traffic

- Use `page_num` for multi-page Google Search requests; strip unsupported `num` and `filter` parameters from the Google URL.
- Group returned organic results by `page_position.page`, with a fallback to the absolute `position` field.
- Do not call balance or task-history endpoints before/after each report.
- The HTML report no longer contains account balance, request estimate, or API cost statistics.
- The balance button makes a single explicit balance request; saving the API key does not trigger an automatic request.
