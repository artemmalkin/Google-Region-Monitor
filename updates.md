# Обновления

## 1.9.4 — прямые URL из 2captcha/HTML перед резервным редиректом

- До сетевого обращения к `google.com/goto` ищутся прямые HTTP(S)-адреса в полях структурированного результата 2captcha: `url`, `link`, `href`, `target_url`, `destination_url`, `original_url`, `final_url`, `resolved_url` и альтернативных вариантах.
- В HTML Google проверяются адресные атрибуты основной ссылки (`href`, `data-url`, `data-href`, `data-dest-url`, `data-target-url`, `data-original-url`, `data-lpage`) и абсолютный URL в `ping`. Относительные `CAES...` токены не превращаются в фиктивные URL на `google.com`.
- JSON и HTML объединяются по результату так, чтобы HTML мог заменить Google `/goto` прямым адресом и сохранить видимую строку `<cite>`.
- Если прямого адреса нет, остаётся резервное разрешение Google `/goto`. Домен из `<cite>` сохраняется и показывается отдельно как подсказка; он не выдаётся за точный URL страницы.
- Отчёт показывает количество прямых адресов из JSON, HTML, резервных разрешений Google и ссылок, для которых доступна только доменная подсказка.
- Автоматические тесты: 38/38 прошли. Проверка реальных редиректов в браузере не выполнялась.

## 1.9.3 — улучшено разрешение Google /goto

- Добавлено чтение заголовка `Location` через `webRequest.onHeadersReceived`, включая ответы, где заголовок присутствует без стандартного 3xx-перенаправления.
- Сохранён `onBeforeRedirect` как дополнительный канал получения конечного URL.
- Оба обработчика работают только для `https://www.google.com/goto*`; конечный адрес проходит прежнюю проверку HTTP(S) и не может оставаться вложенной Google redirect-ссылкой.
- Тайм-аут ожидания увеличен до 12 секунд. Случаи, когда Google не выдаёт `Location` или отклоняет запрос, по-прежнему остаются неразрешёнными — 100% гарантия невозможна.

## 1.9.2 — преобразование новых ссылок Google /goto в прямые адреса

- Добавлено распознавание ссылок `https://www.google.com/goto?url=...` из результатов Google.
- Конечный URL запрашивается у Google через GET без перехода на сайт назначения; адрес берётся из HTTP-заголовка `Location`.
- Преобразование выполняется до региональной проверки ChatGPT и генерации HTML-отчёта, поэтому прямые ссылки используются и в основном списке, и в списке скрытых результатов.
- Если Google не возвращает конечный адрес, исходная ссылка сохраняется; отчёт и журнал показывают количество таких ссылок.
- Добавлено разрешение Chrome `webRequest`, ограниченное наблюдением за переходами `www.google.com/goto`; страницы сайтов назначения не загружаются.

## 1.9.1 — упрощение API и исправление статистики 2Captcha

- Удалена встроенная консоль ручных тестовых запросов 2Captcha, её интерфейс, скрипты, стили и отдельные тесты. Обычный мониторинг, сохранение API-ключа и экспорт API-лога сохранены.
- Для каждого выражения в режиме `google_search` создаётся одно API-задание с `page_num`, равным выбранному числу страниц (1–10). Для нескольких страниц `with_html: true` возвращает HTML в том же ответе; дополнительные задания с `start=10`, `start=20` и далее не создаются.
- Режим `scrape` не меняет схему работы: для каждой выбранной страницы по-прежнему создаётся отдельное задание `task_type: "scrape"`.
- Ручное обновление статистики получает баланс и историю `google_search`/`scrape`. Средняя стоимость для выбранного API-режима считается по завершённым заданиям `done` из поля истории `price`; стоимость последнего отчёта подтверждается по сохранённым `response_id`.
- История не запрашивается автоматически. Диагностическое `x-debug.price` не используется как фактическая стоимость.

## 1.10.1 — исправлено ложное определение CAPTCHA в HTML Scrape

- Исправлен детектор CAPTCHA: обычный JavaScript Google (`hasCaptchaSupport=true`, универсальные обработчики `/sorry/index`) больше не считается страницей проверки.
- Проверяется видимый текст HTML после удаления `script`, `style`, `noscript`, SVG и `template`, а также конкретные challenge-элементы (`form#captcha-form`, форма `/sorry/index`, reCAPTCHA iframe/контейнер).
- Проверена диагностика по реальному ответу 2Captcha: HTTP 200 и HTML содержат обычную выдачу Google с 7 заголовками органических результатов; прежняя версия ошибочно останавливала сбор до перехода к страницам 2–3.

## 1.10.0 — отдельный режим постраничного 2Captcha Scrape

- Добавлен новый источник выдачи «2Captcha Scrape (HTML каждой страницы)»; существующий режим `google_search` сохранён отдельно.
- Для каждой выбранной страницы отправляется отдельное задание `task_type: "scrape"` с `data_format: "raw"` и `format: "json"`; используется HTML из поля `body`.
- Пагинация выполняется обычным URL Google: первая страница без `start`, следующие — `start=10`, `start=20` и далее. Настройки региона, языка, периода и `filter=0` передаются в URL.
- Добавлен локальный разбор HTML Google на заголовки, ссылки и сниппеты. Успешно загруженные страницы фиксируются в отчёте даже при отсутствии распознанных органических ссылок.
- При CAPTCHA/ограничении Google или целевом HTTP 403/429 дальнейшие задания останавливаются. Не полученные страницы отражаются как отсутствующие.
- Диагностический JSON-лог включает каждое задание и сырой ответ Scrape; API-ключ и Authorization маскируются.

## 1.9.8 — исправление offset-пагинации 2Captcha

- Страница 1 запрашивается отдельно: базовый URL без `start`, с `page_num: 1`.
- Страница 2 запрашивается через `start=10` без `page_num` — специальный режим из документации.
- Страницы с третьей запрашиваются через `start=20` с `page_num=max(2, N-2)`. Для выбранных трёх страниц API получает диапазон 3–4, но страница 4 исключается из отчёта.
- Убран прежний запрос `start=20` с `page_num=1`, который в логе v1.9.7 вернул `no_results`.
- На один поисковый запрос приходится не более трёх последовательных API-заданий. Автоматические запросы баланса и истории отключены.

- Выпадающие списки стандартных и пользовательских профилей сортируются по алфавиту.

## 1. Подготовка репозитория

1. Создайте публичный репозиторий GitHub.
2. Загрузите в корень репозитория все файлы полного исходного архива.
3. Убедитесь, что существует `config/standard-profiles.json`.
4. Параметры проекта уже заданы в `github-config.js`: `artemmalkin/Google-Region-Monitor`, ветка `master`, путь `config/standard-profiles.json`. При необходимости измените их там до сборки.

## 2. Обновление стандартных профилей

Стандартные профили хранятся в `config/standard-profiles.json`. Отредактируйте массив `profiles` и сделайте commit/push. Пример одного элемента:

```json
{
  "id": "indonesia",
  "name": "Индонезия",
  "interfaceLang": "id",
  "resultLangs": "id, en",
  "region": "ID",
  "queries": [
    "rosatom",
    "\"rosatom\" AND \"rooppur\""
  ]
}
```

`id` должен быть уникальным в массиве. После commit расширения пользователей получат изменения:

- вручную — по кнопке **Проверить обновление** (она же проверяет GitHub Release);
- автоматически — примерно раз в 24 часа через Chrome Alarms и при запуске Chrome, если с предыдущей синхронизации прошло 24 часа.

Для загрузки используется публичный Raw URL `raw.githubusercontent.com`. При ошибке загрузки предыдущий стандартный список остаётся на месте. Локальные пользовательские профили не изменяются.

Подробная схема описана в [STANDARD_PROFILES.md](STANDARD_PROFILES.md), JSON Schema находится в `config/standard-profiles.schema.json`.

## 3. Добавление, редактирование и удаление стандартных профилей из расширения

Вставьте Fine-grained Personal Access Token с разрешением `Contents: Read and write` только для нужного репозитория.

- **Добавить мой профиль в GitHub** публикует выбранный пользовательский локальный профиль.
- **Сохранить изменения стандартного профиля в GitHub** обновляет стандартную запись с сохранением её постоянного `id`.
- Кнопка **×** рядом с выбором стандартного профиля удаляет его из `config/standard-profiles.json` после подтверждения.

Все три операции выполняются через GitHub Contents API и создают commit в настроенной ветке. Перед обновлением/удалением расширение читает актуальный файл и использует его SHA. При конфликте из-за параллельного commit действие завершается ошибкой без перезаписи более новой версии; нажмите «Проверить обновление» и повторите. После успешного commit расширение принудительно синхронизирует список.

Обычная кнопка «Сохранить профиль» по-прежнему создаёт локальную копию стандартного профиля и не изменяет общий список. Токен остаётся в локальном хранилище расширения и не попадает в экспорт профиля/конфигурации. Не коммитьте токен в GitHub и не передавайте его другим пользователям.

## 4. Публикация новой версии расширения

В `manifest.json` увеличьте номер `version`, отправьте коммит в GitHub и создайте соответствующий тег. Например:

```bash
git tag v1.4.0
git push origin v1.4.0
```

Workflow `.github/workflows/release.yml` проверит совпадение тега и `manifest.json`, соберёт `google-region-monitor.zip` и приложит архив к GitHub Release.

Расширение проверяет последний Release и предлагает скачать новый ZIP. У распакованной установки Chrome обновление файлов автоматически не устанавливается: после скачивания пользователь должен распаковать новую версию и перезагрузить расширение через `chrome://extensions`. Для штатного автообновления файлов расширения используйте Chrome Web Store.

## Примечание об истории v1.5.4

В исходном архиве v1.5.4 `GITHUB_UPDATES.md` содержит записи до v1.5.1 включительно и не содержит отдельного раздела v1.5.4. Поэтому интерфейс не должен приписывать v1.5.4 функции, добавленные в v1.8.0 и позднее. Новая логика показывает только точное совпадение версии; при отсутствии раздела выводится явное сообщение.
